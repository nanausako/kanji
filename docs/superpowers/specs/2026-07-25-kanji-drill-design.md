## 1. 目的と背景

iPad と Apple Pencil で使える漢字テスト web アプリを作る。例文とともに漢字を出題し、
**書き順**を自動判定しつつ、**止め・はね・はらい**は「本人の筆跡にお手本を重ねて、子ども自身が
見比べて気づく」方式で学習させる。日本の学校で習う書き順・字形に準拠する。

対象漢字（初期 10 字。今後追加していく前提 — §3.3 参照）:

| # | 漢字 | 例文 | 読み |
|---|------|------|------|
| 1 | 下 | 机《つくえ》の〇に本《ほん》がある。 | した |
| 2 | 一 | かけっこで〇番《ばん》になった。 | いち |
| 3 | 雨 | 明日《あした》は〇がふるそうだ。 | あめ |
| 4 | 王 | ライオンは百獣《ひゃくじゅう》の〇さまだ。 | おう |
| 5 | 円 | 百《ひゃく》〇のガムを買《か》う。 | えん |
| 6 | 右 | 次《つぎ》の信号《しんごう》を〇にまがる。 | みぎ |
| 7 | 音 | きれいなピアノの〇がする。 | おと |
| 8 | 火 | キャンプで〇をおこす。 | ひ |
| 9 | 花 | 春《はる》になって〇が咲《さ》いた。 | はな |
| 10 | 貝 | 海辺《うみべ》できれいな〇を拾《ひろ》う。 | かい |

### 1.1 例文のふりがな方針（総ルビ）

**例文中の漢字にはすべてふりがな（ルビ）を振る（総ルビ）。上位学年の漢字も自由に使ってよい。**

理由: 小 1 の子はまだ読めない漢字が多いが、ふりがなを振れば読める。むしろ例文でいろいろな漢字に
触れておくことが次の学習につながる（子ども向けの本が総ルビなのと同じ発想）。出題字（空欄 `〇`）は
ルビを振らず、読みを別途 `〇（よみ）` の形で示す（§4.1）。

**表記ルール**: 例文データはルビを `漢字《よみ》` 記法で持つ（青空文庫式）。アプリが `<ruby>` 要素に
レンダリングして表示する。`《...》` は直前の連続する漢字（maximal run）に付く。読みの付く範囲が
曖昧なとき（直前が漢字連続でない等）は `｜漢字《よみ》` の `｜` で base の開始位置を明示する。
`〇` は出題字の空欄なのでルビを振らない。

例: `机《つくえ》の〇に本《ほん》がある。` → 「机（つくえ）の〇に本（ほん）がある。」

漢字を追加する際も、例文中の漢字には同様に総ルビを振る（配当学年による語彙制限は設けない）。

## 2. 主要な設計判断

1. **判定レベル**: 書き順は自動判定。止めはねはらいは「お手本重ね表示 → 子ども自身が
   気づく」方式。機械的な減点はしない。
2. **公開方法**: GitHub Pages でホスト（`https://nanausako.github.io/kanji`）。
   iPad Safari で開き、ホーム画面に追加してアプリ風に使う。更新は git push のみ。
3. **書き順データ**: KanjiVG（日本語書き順）を採用。中国語データでは「右」等の書き順が
   日本と異なるため。ライブラリ・データともにリポジトリ同梱で **CDN 依存なし・完全オフライン**。
4. **描画/判定エンジン**: Hanzi Writer に依存せず、KanjiVG の中心線を自前で SVG 描画し、
   判定用の median（点列）だけを生成して**自前の書き順マッチャで判定**する（→ §10 で経緯）。
   これにより (a) 変換の最難関「中心線→アウトライン化」が不要、(b) 筆跡保存と書き順判定の
   両立問題（旧 §4.3 の dual-capture）が消える、(c) 外部ライブラリ依存が減る。

## 3. アーキテクチャ

ビルド不要のバニラ HTML/CSS/JS 静的サイト（技術選定の根拠と依存の線引きは §3.4）。

```
kanji/
├── index.html          # 画面（1 ページ）
├── src/
│   ├── app.js          # 出題フロー・画面制御
│   ├── ink.js          # ペン入力キャプチャ（パームリジェクション込み）＋ 筆跡描画
│   ├── judge.js        # 書き順判定（drawn polyline ↔ 参照 median のマッチ）
│   └── overlay.js      # お手本アニメーション再生・お手本重ね表示
├── style.css           # スタイル
├── manifest.json       # ホーム画面追加用（§3.4）
├── sw.js               # cache-first Service Worker（オフライン動作・§3.4）
├── data/
│   ├── kanji-data.js   # 10 字の { kanji, sentence, reading, strokes, medians }
│   └── NOTICE          # KanjiVG 帰属表示（CC BY-SA 3.0）
├── tools/
│   ├── kanji-list.json      # 人手で管理する字の一覧（字・学年・読み・例文）＝単一の情報源
│   └── convert-kanjivg.mjs  # kanji-list.json + KanjiVG(SVG) → data/kanji-data.js（開発時のみ実行）
├── LICENSE             # 本コードのライセンス（MIT）
└── LICENSE-DATA        # 派生データのライセンス（CC BY-SA 3.0）
```

### 3.1 コンポーネントと責務

- **index.html**: 画面構造（例文表示 / 書くマス（SVG + キャンバス）/ ボタン群）。
- **style.css**: レイアウトとスタイル。iPad 縦横両対応。十字ガイド、`touch-action: none`。
- **data/kanji-data.js**: `KANJI_DATA` 配列。各要素 `{ id, kanji, grade, reading, sentence, strokes, medians }`（→ §3.3）。
  - `strokes`: KanjiVG の各画の中心線 path（そのまま SVG 描画。丸端で教科書体風に表示）。
  - `medians`: 各画を等間隔サンプリングした点列（判定に使う。KanjiVG から生成）。
  - `sentence`: `漢字《よみ》` のルビ記法を含む例文文字列（§1.1）。`〇` が出題字の空欄。
- **src/ink.js**: Pointer Events でペン軌跡を取得し、本人の筆跡をキャンバスに描画。
  パームリジェクション（§6）を担う。取得した軌跡を polyline として judge へ渡す。
- **src/judge.js**: 描いた画（polyline）と、期待される次の画の median を比較し、
  始点/終点の近さ・方向・形状の類似で「順番・向きが合っているか」を判定する（§4.3）。
- **src/overlay.js**: 「お手本」ボタンで正しい書き順を順にアニメーション再生。
  「答え合わせ」で KanjiVG の字形を薄く重ねて表示。
- **src/app.js**: 出題字のランダム抽出（§3.3）と出題フロー、各コンポーネントの結線、メッセージ表示。
  例文の `漢字《よみ》` 記法を `<ruby>漢字<rt>よみ</rt></ruby>` に変換して表示する（総ルビ・§1.1）。
  変換は小さなヘルパ関数として実装し、単体でテストできるようにする。

### 3.2 データ生成（開発時に一度だけ）

`tools/convert-kanjivg.mjs` で KanjiVG の SVG → `data/kanji-data.js` を生成する。
子どもが使うときは変換不要（静的データ）。**medians の品質がそのまま判定精度になる**ため、
生成物は下記の検証基準で確認する。

**KanjiVG と描画/判定で必要な形式の差分**（変換で吸収する点）:

| 項目 | KanjiVG | 本アプリで必要な形式 |
|------|---------|--------------------|
| 座標系 | 109×109 viewBox | そのまま利用（SVG viewBox を 109×109 に設定） |
| stroke | 中心線 1 本の `<path>`（線） | 中心線 path をそのまま SVG 描画（丸端）。アウトライン化は**しない** |
| median | 存在しない | path を等間隔サンプリングして点列を生成（判定用・必須） |

補足: Hanzi Writer 形式は 1024×1024・Y 軸反転・塗り輪郭（アウトライン）を要求し、
中心線→アウトライン化が最大工数になる。本アプリは Hanzi Writer に依存しないため、
この変換は不要。座標系も KanjiVG の 109×109 をそのまま使う。

**変換の検証基準**:

- 画数一致: 生成した strokes / medians の本数が、その漢字の正しい画数と一致する。
- 順序一致: strokes / medians の並び順が KanjiVG の記載順（＝日本語書き順）と一致する。
- median 妥当性: 各 median の始点・終点が対応する中心線 path の端点と概ね一致する。
- 目視: 全字がアニメーション再生で正しい日本語書き順になる（特に「右」ノ→一）。

### 3.3 漢字の追加とランダム出題

初期 10 字から**字を増やしていき、その中からランダムに出題する**ことを前提に設計する。

**データ構造**:

```js
{ id: '04e0b', kanji: '下', grade: 1, reading: 'した',
  sentence: '机《つくえ》の〇に本《ほん》がある。', strokes: [...], medians: [...] }
```

- `id`: Unicode コードポイント 5 桁 hex 小文字。KanjiVG のファイル名（`04e0b.svg`）と 1:1 で対応し、
  重複追加の検出キーになる。
- `grade`: 配当学年。将来の学年別出題（§8 でスコープ外）の下地として持たせておく。
  例文の語彙は総ルビ方針（§1.1）なので `grade` による制限はしない。

**出題の選び方**:

- セッション開始時に、全 `KANJI_DATA` から `QUESTION_COUNT`（既定 10）字を
  **重複なしランダム抽出**する（Fisher-Yates でシャッフルして先頭 M 件）。
- 登録字数が `QUESTION_COUNT` に満たない場合はあるだけ出す（`Math.min` で丸める）。
- 抽出の母集団は**データ検証を通った字だけ**にする。§6 の「読めない字はスキップ」を
  ランタイムではなく**抽出前**に行うことで、出題数と進捗表示がずれない。
- 進捗表示（`問題 3 / 10`）の分母はハードコードせず、抽出した配列長を使う。

**セッションをまたぐ出題履歴は持たない**（§5 の「記録を持たない」方針を維持）。
「前回と同じ字が出た」は許容する。字数が増えれば体感の重複は自然に減るうえ、
履歴を持つとスコア管理に近づき、避けたいプレッシャー要因になるため。

**字を追加する手順**:

1. KanjiVG から対象字の SVG を用意する（ファイル名 = コードポイント 5 桁 hex 小文字）。
2. `tools/kanji-list.json` に `{ id, kanji, grade, reading, sentence }` を追記する。
   例文は §1.1 の総ルビ方針（`漢字《よみ》` 記法）で書く。
3. `node tools/convert-kanjivg.mjs` を実行し `data/kanji-data.js` を再生成する。
4. §3.2 の検証基準（画数・順序・median 妥当性）が自動で走り、失敗したらエラー終了する。

例文などの人手データは `tools/kanji-list.json` を単一の情報源とし、生成物である
`data/kanji-data.js` は**手で編集しない**（再生成で失われるため）。

**データ量と分割方針**: 1 字あたり strokes + medians でおよそ 2〜5 KB。小 1 配当 80 字なら
200〜400 KB 程度で単一ファイルのまま問題ない。**300 字を超えたら**学年別ファイル
（`data/kanji-g1.js` 等）に分割し、必要な学年だけ読み込む構成に切り替える。

### 3.4 技術スタックと依存方針

| 層 | 選定 | 理由 |
|---|---|---|
| ランタイム | 素の **ES Modules**（フレームワークなし） | 下記 |
| 型 | **JSDoc + `// @ts-check`**（`tsc --noEmit` で検査のみ） | ビルド成果物ゼロのまま型が効く。TypeScript 導入はビルド必須化を招くので採らない |
| 描画 | SVG（お手本）+ Canvas 2D（筆跡）+ Pointer Events | 追加ライブラリ不要 |
| データ生成 | Node.js + `svg-path-properties`（devDependency） | median 生成に path 長サンプリングが要る（下記） |
| テスト | `node:test`（Node 標準）+ Playwright | 追加ランナー不要 |
| CI/配信 | GitHub Actions → GitHub Pages | |

**フレームワークを入れない根拠**: 保持する状態は「現在の問題 index / 現在の画 index / ミス回数 /
筆跡」程度しかなく、宣言的 UI の恩恵がほぼない。逆に中核である Canvas 描画と SVG アニメーションは
命令的操作そのもので、React に載せても全部 `useRef` + `useEffect` に閉じ込めることになり抽象化が
仕事をしない。§2 の「更新は git push のみ」とも噛み合う。

**依存の線引き**（§2-3 の「CDN 依存なし」の正確な意味）:

- **ランタイム依存はゼロ**。配信物（html/css/js/data）に第三者ライブラリを含めない。
- **開発時依存は許容**。`devDependencies` は配信物に入らないため、上記方針と矛盾しない。
  KanjiVG の path から median を等間隔サンプリングするにはブラウザの `getPointAtLength()` 相当が
  必要だが **Node には存在しない**ため、`svg-path-properties` を使う（自前実装も可能だが車輪の再発明）。

**モジュール形式**: `data/kanji-data.js` はグローバル変数ではなく `export const KANJI_DATA = [...]`
の ESM とする。`judge.js` 等を `node --test` から `import` して単体テストするための前提条件
（グローバル前提だとテスト時にダミーのグローバルが要る）。

**ローカル開発**: ES Modules は `file://` では CORS で動かない。`python3 -m http.server` 等の
静的サーバ経由で開く（GitHub Pages 上では問題ない）。

**PWA（ホーム画面追加とオフライン）**: §2 の「ホーム画面に追加してアプリ風に使う」「完全オフライン」を
成立させるには以下が要る。**どちらも構成に含める**:

- `manifest.json` ＋ `index.html` の `apple-mobile-web-app-capable` メタタグ
  → 無いとホーム画面に追加してもスタンドアロン表示にならず、Safari の UI が出たままになる。
- `sw.js`（cache-first の自前 Service Worker、20 行程度）
  → 無いとオフライン動作はブラウザキャッシュ任せで保証されない。Workbox 等のツールは不要。

## 4. 画面と UX

### 4.1 レイアウト

```
┌─────────────────────────────┐
│  問題 3 / 10                  │  ← 分母は出題数（§3.3）
│  明日は〇（あめ）がふるそうだ。 │  ← 例文（漢字は総ルビ／出題字は〇+読み）
├─────────────────────────────┤
│   ┌───────────────┐         │
│   │   ╎           │         │  ← 書くマス（十字ガイド付き）
│   │ ┈┈┼┈┈┈       │         │     Apple Pencil で書く
│   │   ╎           │         │
│   └───────────────┘         │
├─────────────────────────────┤
│ [お手本] [やり直す] [答え合わせ]│
└─────────────────────────────┘
```

書くマスは、下層に SVG（お手本・アニメーション用）、上層に透明キャンバス（本人の筆跡）を
重ねた構造。本人の筆跡は常に上に残るので、止めはねはらいが視認できる。

### 4.2 止めはねはらい比較のしくみ（中核）

1. 子どもが Apple Pencil でマスに漢字を書く → **本人の生の筆跡（インク）がそのまま残る**
   （止め・はね・はらいが視認できる）。
2. 一画ごとに judge が**書き順を自動チェック**（間違った順・逆向きなら通知）。
3. 「答え合わせ」を押すと → **本人の筆跡の上に、正しいお手本（KanjiVG 字形）を薄く重ねて表示**。
4. 子ども自身が「はねが足りない」「はらいが止まっている」と**見比べて気づく**。

機械が「はねが 1mm 短い」と減点するのではなく、お手本と重ねて自分で気づく方式。

### 4.3 書き順判定（judge.js）の考え方

対象は 10 字・1〜8 画・低学年向けの寛容判定なので、シンプルなマッチで十分。

- 期待する画の順に、本人が描いた画（polyline）を照合する。
- 各画の判定要素: 始点が期待 median の始点に近いか / 終点が終点に近いか / 全体の向き
  （ベクトル方向）が一致するか / 極端に形が違わないか。
- 合致 → 次の画へ。不一致 → 「順番か向きがちがうよ」と表示し、その画をやり直させる。
- 2 回ミスで、次に書く画の中心線をマスに薄くヒント表示。
- しきい値は実機で調整（子どもが書くと崩れるため、寛容側に倒す）。

## 5. 操作の流れ・ボタン

- 登録字からランダム抽出した `QUESTION_COUNT` 問（既定 10、§3.3）を順に出題 → 各問クリアで
  「次へ」→ 全問終了で「ぜんぶできたね！🎉」お祝い画面。
- スコア・記録は持たない（YAGNI。低学年の自習用でプレッシャーを与えない）。
- 出題は毎回シャッフルされるので、同じ字が続けて出ることは許容する（§3.3）。

| ボタン | 動作 |
|--------|------|
| お手本 | 正しい書き順を順にアニメーション再生（overlay.js） |
| やり直す | 今の字（筆跡・進捗）を消してもう一度書く |
| 答え合わせ | 本人の筆跡にお手本を薄く重ねて表示（overlay.js） |

- 例文は空欄「〇」＋読みガナ表示。

## 6. 入力処理・パームリジェクション・エラー処理

**パームリジェクション**（iPad + Apple Pencil で低学年が書く前提。手のひらの接触が
線になると中核機能が壊れるため必須）:

- Pointer Events の `pointerType` で分岐する。`pen`（Apple Pencil）を優先。
- 一度でも `pen` イベントを観測したら、以後その字の間は `touch`（手のひら・指）を無視する。
- Apple Pencil を持たない環境では `touch` 描画にフォールバック（pen 未観測時のみ）。

```js
// 概念コード（実装は src/ink.js）
if (e.pointerType === 'touch' && penSeen) return; // pen 検出後は touch を捨てる
```

**その他**:

- `touch-action: none` でスクロール誤爆を防止。
- 書き順データが不正な字があればコンソール警告 ＋ **出題候補の母集団から除外**する
  （§3.3。出題開始前に弾くので、進捗表示の分母とずれない）。全体は止めない。

## 7. テスト方針

- 変換後、全字が正しい**日本語書き順**でアニメーション再生されるか目視確認
  （特に「右」ノ→一）。画数・順序の自動検証（§3.2 の検証基準）も実施。
- judge.js: 代表的な「正しい順」「逆順」「逆向き」入力に対する判定を検証。
- ルビ変換ヘルパ: `漢字《よみ》` / `｜漢字《よみ》` / ルビなし文 / 複数ルビ混在を
  正しい `<ruby>` に変換できることを単体テストで検証（§1.1）。
- 出題抽出: 重複が出ないこと・登録字数 < `QUESTION_COUNT` でも落ちないこと・
  不正データの字が抽出されないことを検証（§3.3）。
- iPad Safari 実機（または Playwright のタッチ/ペンエミュレーション）で、描画・
  パームリジェクション・書き順判定・お手本重ね表示の動作を確認。

## 8. スコープ外（今回はやらない）

- 機械による止めはねはらいの自動採点・減点。
- スコア保存・履歴・ランキング。
- **セッションをまたぐ出題履歴**（前回出た字を避ける等）。§3.3 の理由により持たない。
- **学年・範囲を選んで出題する UI**。`grade` はデータに持たせておくが、初期版は全字が母集団。
- 送りがな・熟語・読みテストなど、書き取り以外の出題形式。

なお**漢字を増やすこと自体はスコープ内**で、§3.3 の手順で追加できる構造にする。

## 10. アーキテクチャ変更の経緯（レビュー反映）

初版は Hanzi Writer の quiz を書き順判定に使い、別キャンバスで筆跡を保存する構成だった。
別セッションのレビューで以下が指摘され、妥当と判断して方針を変更した。

- KanjiVG → Hanzi Writer 形式変換は、座標系（109×109→1024×1024・Y 反転）に加え
  **中心線→塗り輪郭（アウトライン化）**が必要で、これが工数の最大リスク。
- Hanzi Writer 主だと、筆跡保存のために quiz と別レイヤで dual-capture する必要があり、
  ポインタイベントの二重取得が不安定になりやすい。
- 代替として「KanjiVG の線を直接描画し、判定用 median だけ生成して自前で書き順判定」する
  ルートなら、アウトライン化が不要になり dual-capture 問題も同時に消える。

結論: 代替案を主案に採用（§2-4）。トレードオフは「書き順マッチャを自前実装する」点のみで、
対象が 10 字・低学年向け寛容判定のため許容範囲と判断した。
